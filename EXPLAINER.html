Relatório · Agent Arena · Fase 5

Modo agente agora isola cada execução num container Docker

Antes, o agente pi rodava o isolamento de execução por worktree ou clone — só uma parede de processo. Com esta fase, cada rep de cada contestant pode correr num container Docker efêmero (isolation.kind = "container"): limites rígidos, key do OpenRouter fora de qualquer arquivo, zero órfão no timeout.

isolation.kind: container 2026-08-23 validado · US$ 0,0201

Resumo em uma frase

A execução do agente pi é isolada por container Docker efêmero: a key entra por --env-file 0600 do host (nunca em volume), os artefatos voltam via volumes /ws+/exec, e o timeout mata por nome sem órfão.

container isolation.kind novo
0600 env-file do host (tmp)
0 órfãos no timeout
US$ 0,0201 run de validação
Escopo (importante): só a execução do agente é isolada pelo container. setup[] e verify[] (oráculo) continuam no host — isolar esses via dockerExec é TODO de fase futura.

Como encaixa na história do modo agente

O modo agente já tinha: executor pi em sala limpa, dossiê determinístico, juiz oráculo+LLM, ledger de custo e superfícies CLI/HTTP/MCP. O isolamento de execução tinha três isolation.kind — worktree (default), clone e container (novo). Em worktree/clone o agente já estava "só" separado por processo; em container ele ganha uma parede de namespace + limites rígidos de memória/processos.

Glossário (definido uma vez só — dobre para abrir)
TermoDefinição

1 · Fluxo da execução em container

Cada execução do pi roda um docker run -i --rm com o container nomeado pb-agent-<execId>, mounts -v <workspace>:/ws + -v <execDir>:/exec, cwd /ws. O que o agente grava aparece no host sem docker cp — os volumes são o corredor de saída.

Host → docker run -i --rm → container → pi → grava em /ws e /exec → artefatos voltam ao host sem docker cp.

Imagem default e conteúdo

A imagem é prompt-builder-pi:<executorVersion> (ex. prompt-builder-pi:0.84.2), derivada da versão pinada do executor. Ela é criada na primeira preparação de run em container (via ensurePiImage, com o Dockerfile embutido em src/agent/container.ts) e cacheada por tag. O default da tag é sobrescrito por isolation.image.

# Dockerfile embutido em src/agent/container.ts (Fase 5)
FROM node:22-bookworm-slim
RUN apt-get update && apt-get install -y --no-install-recommends git ca-certificates bash
RUN npm install -g @earendil-works/pi-coding-agent@<ver>

2 · Caminho da key (env-file 0600, nunca no volume)

A key do OpenRouter entra por um --env-file tmp 0600 no host (via os.tmpdir()), apagado ao fim do run. Nunca em arquivo de volume/container, nunca em argv — o argv.json de auditoria mascara o caminho como <env-file-tmp-0600>. A verificação é a prova: grep sk-or- → NONE na run inteira e pi-home/auth.json = {}.

A key vive só no env do processo do container; o env-file é apagado ao fim e o audit mascara o caminho no argv.json.
Prova da sala (spike + validação): grep -rl sk-or- no host e no volume → NONE; env | grep OPENROUTER_API_KEY → 1 (só no env do pi); pi-home/auth.json vazio.

3 · Cycle kill/timeout — sem órfão

No timeout/cancelamento o CLI docker não basta (matar o CLI não derruba o container). O produtor mata o container por nome: docker kill <nome> + docker rm -f <nome> (fire-and-forget, idempotente). O --rm cobre o exit normal; o kill explícito cobre o resto. Resultado: nenhum processo pi e nenhum container órfão no host.

Timeout/cancelamento ⇒ docker kill + docker rm -f por nome; nenhum órfão no host.
Correção crítica do spike — só com -i funciona

No comando do produtor original o container recebia stdin vazio: sem -i (--interactive), o stdin pipeado da tarefa vira EOF e o pi sai com exit 0 e só o evento session. No --mode json não-interativo, a tarefa entra pelo stdin pipeado — logo o spawn do docker precisa de -i com stdin = task. Também não existem as variáveis PI_TASK/PI_SYSTEM_PROMPT/PI_MODEL_ID no pi: as reais são PI_MODEL, PI_PROVIDER, PI_KEY.

Doctor com preflight de Docker

O agents doctor ganhou a flag --container (e o --deep como canário). Quando o modo é container, o preflight exige CLI Docker no PATH + daemon acessível (sem sudo) + imagem; se faltar, exit 3 — o run nem tenta.

prompt-builder agents doctor            # modo worktree/clone
prompt-builder agents doctor --deep      # auto-teste de sala limpa
prompt-builder agents doctor --container # preflight docker
prompt-builder agents doctor --deep --container

O pré-voo ecoa · docker ok (prompt-builder-pi:<ver>) ou docker CLI AUSENTE / imagem ausente. O doctor não builda — se a imagem faltar, rode uma run em container para buildá-la na primeira preparação (ensurePiImage). O canário de sala limpa pode rodar em container via --deep --container.

FlagO que fazExit se falhar
agents doctorProva a sala limpa (canários, versão pinada, git, disco)3
--deepAuto-teste de sala limpa (pode rodar o canário em container)3

Antes → Depois (Fase 5)

Antes
  • Isolamento de execução por worktree (git worktree da raiz-de-mundo) ou clone descartável.
  • Parede só de processo; os artefatos vivem no workspace do host.
  • Key lida do ~/.pi/agent/auth.json no processo.
Depois
  • Novo isolation.kind = "container": cada execução num container efêmero.
  • Parede de namespace + -m 2g --pids-limit 512 e --user do host.
  • Key por --env-file 0600 do host, nunca em volume/argv; apagado ao fim.
  • Kill por nome (docker kill + docker rm -f), zero órfão.

Contrato de config (novo)

{
  "agent": {
    "executor": "pi",
    "executorVersion": "0.84.2",
    "promptMode": "append",
    "limits": { "maxTurns": 30, "maxCostUsd": 0.40 },
    "isolation": { "kind": "container" }   // worktree (default) | clone | container
  }
}

isolation.image opcional — sobrescreve a tag prompt-builder-pi:<executorVersion>.
